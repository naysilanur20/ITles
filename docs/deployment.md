# Развёртывание и обслуживание сервера

Эта инструкция для владельца сервера, не для администратора компании.
Регистрация компании и индивидуальные доступы настраиваются через веб:
[администратору](administrator.md), [пользователю](user-guide.md).

## Нужен полный стек

Шаблон статического сайта находит `frontend/package.json`, собирает Vite и
копирует только `dist` в Nginx. Это размещает интерфейс, но **не запускает
Python API и SQLite**. Тогда `GET /api/health` может возвращать HTML с кодом
200, а `POST /api/auth/login` и `POST /api/auth/demo` — Nginx 405.
Успешная сборка фронтенда не доказывает работоспособность входа.
HTML/405 от статического nginx встречался в прежнем размещении. Это не диагноз
нынешнего отказа: точный адрес пользовательского сбоя пока не предоставлен.

## Deploy-F: архив с собственным Dockerfile

Deploy-F [заявляет поддержку архивов с Dockerfile](https://deploy-f.com/all-hostings/hosting-docker).
Точные названия полей текущей панели не проверены; ниже необходимые параметры,
а не предположение о её кнопках.

1. Загрузите **`itles_deploy.zip`**. В нём `Dockerfile` находится непосредственно
   в корне архива, рядом с `backend/`, `frontend/` и `server.py`.
2. Выберите сборку **по собственному Dockerfile**, а не шаблон
   React/Vite/Node → Nginx. Контекст сборки — корень архива, путь — `Dockerfile`.
   Папку `frontend` и выходной каталог `dist` отдельно указывать не нужно.
3. Внутренний HTTP-порт — **8080**. Публичный адрес должен использовать HTTPS;
   прокси должен сохранять исходный заголовок `Host` для проверок Origin.
4. Для учебного просмотра задайте `ITLES_DEMO_ENABLED=1` и
   `ITLES_COOKIE_SECURE=1`. Переменная `PORT`, если панель её задаёт,
   должна совпадать с внутренним портом. Для реальной организации demo выключен.
5. Подключите **постоянный диск в `/data`**, доступный UID/GID `10001:10001`.
   Путь БД по умолчанию — `/data/itles.sqlite3`.
   Само наличие `VOLUME` в Dockerfile не гарантирует сохранность данных при
   повторном размещении у провайдера: диск должен явно повторно подключаться
   к новому контейнеру. Без этого нельзя использовать реальные данные.
6. Запустите новую сборку. В финальном образе должен быть Python,
   в журнале запуска — Uvicorn, **не только** `nginx:alpine`.
7. Откройте `/api/health`: ожидается JSON со `"status":"ok"`, не страница входа.
   Затем нажмите «Посмотреть демо». Регистрация компании выполняется отдельно
   через «Я администратор компании»; обычный вход не создаёт аккаунт.

Если панель позволяет только статический шаблон, нужен режим Docker/контейнера
или помощь поддержки хостинга. Разрешение POST в статическом Nginx, CORS `*`
и смена пароля отсутствующий API не исправляют.

## Отдельный VPS с Docker Compose

Архив распаковывается в отдельный каталог. Не заменяйте конфигурацию чужого
приложения на сервере. Для вымышленного учебного парка за HTTPS-прокси:

```sh
ITLES_DEMO_ENABLED=1 docker compose -f deployment/compose.yaml up -d --build
docker compose -f deployment/compose.yaml logs --tail=60 itles
curl --fail http://127.0.0.1:8080/api/health
```

`deployment/compose.yaml` публикует порт только на loopback VPS. Настройте существующий
TLS-прокси на `127.0.0.1:8080` с сохранением `Host`; его конфигурация зависит
от сервера. При прямом локальном HTTP cookie Secure не отправляется браузером.
Не отключайте Secure для публичного домена — используйте HTTPS.
Compose создаёт именованный том `itles-data`; не удаляйте его командами
`docker compose -f deployment/compose.yaml down -v` или очисткой томов. Не меняйте имя Compose-проекта
без явного повторного подключения прежнего тома.

После запуска администратор создаёт компанию через веб. В образе нет
предустановленной компании или общего пароля. `backend.cli` остаётся
служебным инструментом оператора, не заменой клиентской регистрации.
Чтобы закрыть только новые регистрации, задайте `ITLES_REGISTRATION_ENABLED=0`.
`ITLES_DEMO_ENABLED` и регистрация независимы. Пароли и токены не передавайте
параметрами команд, в Git, скриншотах или журналах.

## Обновление и миграция существующей базы

Не удаляйте БД и не пересоздавайте том. Перед обновлением получите проверенную
копию через SQLite backup API, а не копирование одного файла работающей WAL-базы:

```sh
python -m scripts.backup_db /data/itles.sqlite3 /data/backups/before-update.sqlite3
python -m scripts.backup_db /data/backups/before-update.sqlite3 --verify-only
```

В контейнере эти команды выполняются через `docker compose exec itles …`.
Путь назначения должен быть новым: инструмент не перезаписывает имеющуюся
копию. Файл создаётся с правами 0600; проверяются целостность SQLite и внешние
ключи. Это не шифрование. Копию нужно перенести в согласованное защищённое
резервное хранилище; копия только на том же диске не защищает от его потери.

Новая схема создаёт таблицы индивидуальных пользователей, сессий, кодов и
настройки источников, сохраняя компании, машины, события и реестр. Версия
миграции записывается в `schema_migrations`. Миграция идемпотентна и применяется
при инициализации БД. Старые организационные сеансы реальных компаний
завершаются, а не превращаются в административные.

Старый общий пароль не доказывает, кто является владельцем компании. До
назначения индивидуального владельца он имеет только переходное чтение
через логин `legacy`. После независимого подтверждения полномочий оператор
выдаёт одноразовый код:

```sh
python -m backend.cli issue-legacy-admin --account company-code --login admin --owner-verified
```

Код передаётся проверенному владельцу защищённым способом. Он активирует
учётную запись через веб и задаёт собственный пароль. Прежний общий доступ
и его сеансы отменяются. Команда не должна заменять уже активного владельца
и не предоставляет способ захвата компании по её названию.

Если администратор потерял пароль и код восстановления (либо код истёк),
оператор после такой же независимой проверки выдаёт новый код активации
**существующему** администратору:

```sh
python -m backend.cli reset-admin-access --account company-code --login admin --owner-verified
```

Команда завершает сеансы только этого администратора, отменяет его пароль и
код восстановления. Пользователи компании и принятые данные сохраняются.
Флаг `--owner-verified` подтверждает выполненную оператором проверку, но не
проводит её автоматически. Код активации действует 72 часа и показывается один раз.

Проверяйте миграцию сначала на копии базы. Сравните количество компаний,
машин, событий и строк объёма до и после. Не применяйте откат приложения
к уже мигрированной БД без проверки совместимости; сохраняйте исходную копию.

## Проверка восстановления и перезапуска

1. Остановите экземпляр, который будет использовать восстановленную БД.
2. Восстановите проверенную копию **в новый путь**, сохранив исходную базу:

   ```sh
   python -m scripts.backup_db /data/backups/before-update.sqlite3 /data/restored.sqlite3
   python -m scripts.backup_db /data/restored.sqlite3 --verify-only
   ```

3. Для изолированной проверки укажите `ITLES_DB_PATH=/data/restored.sqlite3`
   и запустите один экземпляр. Не направляйте его одновременно на рабочую
   базу и не удаляйте WAL/SHM работающего процесса.
4. Проверьте вход, состав компаний и машин, выборку событий и выгрузку.
   Перезапустите с тем же диском и проверьте сохранение настроек ещё раз.
5. Только после проверки и согласования переключайте рабочий сервер.

Копия содержит хеши и действующие сессии/коды на момент снимка. Для восстановления
после компрометации нужны отдельный отзыв сессий и ротация секретов; исправная
SQLite не доказывает безопасность содержимого резервной копии.

## Проверка и границы

```sh
python -m scripts.check_deployment --url https://your-host.example
python -m scripts.check_deployment --url https://your-host.example --demo
```

Нужен Python 3.12 с зависимостями проекта. Первая команда не передаёт пароль:
проверяет JSON health, отказ доступа без сессии и валидацию POST входа.
Вторая создаёт временную **учебную** сессию, проверяет чтение списка машин и
завершает её. Это не проверка реального аккаунта, OEM-данных или визуального UI.

После размещения отдельно проверьте браузером карту, показатели, выход из
сессии и повторный вход. Для постоянной БД создайте отдельную тестовую
организацию, пересоздайте контейнер **с тем же томом** и проверьте вход снова.
До реальных данных нужны резервное копирование и пробное восстановление,
согласование площадки и остальные меры из README. Один процесс намерен:
ограничители попыток и общего бюджета авторизации локальны процессу, не
распределены между репликами. Не запускайте несколько worker-процессов с
ожиданием общего лимита. Для внешнего сервера также нужны лимиты на TLS-прокси,
контроль дискового места, обслуживание обновлений и правила хранения данных.

## Диагностика входа без раскрытия секретов

Проверьте факты, а не историческую причину:

- URL, HTTPS, текущую версию `/api/health` и дату обращения.
- `/api/auth/options`: включены ли demo и регистрация.
- POST на `/api/auth/demo`: HTTP-статус и JSON, а не HTML от статического шаблона.
- Следующий `/api/auth/me`: успешный POST без этого запроса ещё не подтверждает cookie.
- Secure, HttpOnly, SameSite и совпадение публичного Host/Origin. Во встроенном
  просмотре браузер может ограничивать cookies; проверьте отдельную вкладку HTTPS.
- Лимит попыток, лимит demo-сеансов, доступность SQLite, свободное место и права диска.

Не отключайте Secure или все лимиты, не удаляйте чужие сессии и не очищайте БД.
UI показывает безопасные сведения для диагностики. Не публикуйте содержимое
cookie/Authorization, тело пакетa или ключи. Сценарий считается восстановленным
только после входа из чистой сессии, выхода и повторного входа на том же адресе.
